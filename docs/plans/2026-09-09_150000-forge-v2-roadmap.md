## 2. The critical path

### Thesis (from research doc §18)

> **A model-agnostic commander agent that can improve its ability to solve a family of tasks by dynamically creating specialized agents and retaining only capabilities that demonstrably improve future outcomes.**

### Minimum experiment that proves the thesis

1. Define a **repeatable task family** with a deterministic tool API (fake but realistic).
2. Run **baseline** — no learned capabilities, measure outcome.
3. **Reflect** on failure → produce a candidate playbook.
4. Run **learning gate** — applicability + A/B trial + held-out no-regression.
5. If validated, **reuse** the playbook on a fresh run.
6. **Measure** improvement: better outcome, fewer tool calls, fewer interventions.
7. **Separate environment**: fresh workers, no conversation carryover.

### The build order

```
Phase 0 — Foundation (DONE, 106 tests)
    schema.py, fleet.py, ledger.py, ao_runner.py, verifier.py, watchdog.py,
    harness.py, evaluation.py, reflection.py, skills.py,
    tooling.py (NEW), playbook.py (NEW), tracing.py, neatlogs.py

Phase 1 — Research experiment (THIS PLAN)
    Goal: run baseline → reflect → evaluate → re-run with validated playbook
    └─ All deterministic, no LLM, no live AO
    └─ CLI surfaces for each step

Phase 2 — Foreground agent loop
    Goal: model calls a tool, runtime judge decides next step
    └─ foreground.py, RuntimeJudge protocol, at least one deterministic judge

Phase 3 — Real AO integration
    Goal: one real worker produces a verifiable artifact
    └─ Worker-side fix (prompt/ACP/model), not controller change

Phase 4 — Learning loop on real AO tasks
    Goal: baseline AO task → reflect → gate → improved AO task

Phase 5 — Cross-harness transfer
    Goal: validated playbook helps a fresh Claude Code or Codex worker
```

## 3. Phase 1 build plan

Build the **deterministic research experiment** that proves the loop works end-to-end with fake tools, a fake model, and measurable improvement. No LLM, no AO.

### Task 1: RunResult comparison contract

**Objective:** Allow two `RunResult`s to be compared for regression.

**Files:**
- Modify: `src/forge/schema.py` — add `def compare(self, other, *, metrics: tuple[str, ...]) -> ComparisonResult`
- Create: `tests/test_schema.py`

```python
@dataclass(frozen=True)
class ComparisonResult:
    regression: bool
    improved: bool
    deltas: dict[str, float | None]
```

Comparison is: passed > failed, fewer tools_called is better, fewer interventions is better, wall_s is informational. Cost/tokens stay null if unavailable.

4 tests:
- `test_compare_improved_pass_rate`
- `test_compare_regression_tool_calls`
- `test_compare_absent_cost_stays_null`
- `test_compare_equal_passes_no_regression`

### Task 2: LearningExperiment runner

**Objective:** Run baseline, generate candidate, run gate, and if validated, run learned.

**Files:**
- Create: `src/forge/experiment.py`
- Create: `tests/test_experiment.py`

```python
@dataclass(frozen=True)
class LearningExperiment:
    experiment_id: str
    task_family: str
    baseline_results: tuple[RunResult, ...]
    candidate: SkillCandidate | None
    gate_verdict: GateVerdict | None
    learned_results: tuple[RunResult, ...] | None
    comparison: ComparisonResult | None
```

The runner:
1. Accepts a `GoalSpec`, a task family, and an `Executor` (for baseline and learned).
2. Runs N baseline trials.
3. Passes baseline evidence to a `reflector` (can be `reflect_failure` or a deterministic stub).
4. Runs `run_candidate_evaluation` on train + heldout cases.
5. If `promote_candidate`, selects the playbook and runs learned trials.
6. Compares: `comparison = baseline.compare(learned)`.
7. Persists everything to the ledger.

Tests:
- `test_experiment_runs_baseline_only_if_no_candidate`
- `test_experiment_skips_learned_if_gate_rejects`
- `test_experiment_wires_validated_playbook_to_learned_run`
- `test_experiment_persists_all_trials_and_evidence`

### Task 3: CLI commands for the experiment

**Objective:** Surface the experiment from the CLI.

**Files:**
- Modify: `src/forge/cli.py`

Three commands:

```
forge experiment <goal.json> --trials N -n experiment-1
forge experiment-results <experiment-id>
forge experiments
```

The `experiment` command:
1. Loads the GoalSpec.
2. Creates an `ExperimentRunner` with a local/fake executor.
3. Runs it.
4. Prints the result.

The `experiment-results` command reads from the ledger.

Tests:
- `test_experiment_cli_with_local_executor` (via `main_from_args_for_test`)
- `test_experiment_cli_reports_gate_verdict`
- `test_experiment_cli_shows_comparison`

### Task 4: Wire playbook selection into FleetController

**Objective:** A validated playbook is automatically selected and injected when the task family matches.

**Files:**
- Modify: `src/forge/fleet.py`
- Modify: `tests/test_fleet.py`

`FleetController` gets an optional `PlaybookRegistry`:
- On `run()`, if the goal has a `context_refs` that matches a task-family fingerprint, select the playbook.
- Inject the ordered steps into the task context.
- During execution, the runner uses the playbook's tool sequence.

Tests:
- `test_controller_selects_validated_playbook_for_matching_task`
- `test_controller_ignores_playbook_for_non_matching_task`
- `test_controller_records_playbook_selection_in_ledger`

### Task 5: End-to-end experiment test

**Objective:** Run the whole loop in one test and show measurable improvement.

**Files:**
- Create: `tests/test_end_to_end_experiment.py`

1. Create a `GoalSpec` for the third-party-auth task family.
2. Register a fake tool that fails when steps are in the wrong order.
3. Run `LearningExperiment` with baseline executor that calls `target_api` without `validate_token` → fails.
4. Reflect on failure → candidate playbook `["validate_token", "target_api"]`.
5. Gate validates it (applicability + A/B benefit + heldout).
6. Learned run uses the playbook → passes.
7. Comparison shows improvement.

This test proves the closed loop without any LLM or live AO.

## 5. The experiment design

### Task family: third-party-auth

A fake but realistic tool API:

```
Tool: validate_token
    input: {"token": str}
    output: {"valid": bool}
    Always succeeds when called first in sequence.

Tool: target_api
    input: {"token": str | None, "action": str}
    output: {"ok": bool}
    Fails if token is None or "invalid".
    Succeeds if token was validated by validate_token.

Tool: verify_deployment
    input: {"artifact_path": str}
    output: {"exists": bool}
    Succeeds if artifact exists at path.
```

### Baseline condition

The naive agent calls `target_api` directly with no token → fails.

### Learned condition

`PlaybookRegistry` returns playbook `auth-setup-v1`:
```
ordered_steps: ["validate_token", "target_api", "verify_deployment"]
```

### Trials

- 3 baseline trials (all fail)
- 3 learned trials (all pass)
- 2 held-out cases (similar but distinct task variations)

### Expected output

```json
{
  "experiment_id": "auth-exp-1",
  "task_family": "third-party-auth",
  "baseline": {"passed": 0, "tool_calls": 3, "interventions": 0},
  "learned": {"passed": 3, "tool_calls": 6, "interventions": 0},
  "comparison": {
    "passed_delta": 3,
    "tool_calls_delta": 3,
    "regression": false,
    "improved": true
  },
  "gate_verdict": "validated",
  "cost_usd": null,
  "tokens_in": null,
  "tokens_out": null
}
```

The null cost/token fields are intentional — the fake tools don't report them.

## 6. Key architectural invariants

From the research doc and current code:

1. **Learning is not memory.** Reflection creates a `candidate`. The gate decides `validated` or `rejected`. The playbook registry stores validated knowledge. Experience is not automatically knowledge.

2. **The verifier is the only authority for pass.** Worker status, model claims, and self-reports are observations, not evidence.

3. **Artifact freshness is mandatory.** A pre-existing unchanged artifact cannot satisfy a new task.

4. **Cost/token null is honest.** Missing provider/runtime data is `null`, never `0` or estimated.

5. **The experiment is the proof.** Components are necessary but not sufficient. The end-to-end test is the deliverable.

6. **AO is an adapter.** The experiment works with fake tools and a fake runner. AO integration is a separate layer.

7. **Neatlogs is a mirror.** The ledger is the source of truth. Neatlogs is optional hosted telemetry.

## 8. What we are NOT building yet

Explicitly deferred, with reasons:

- **Foreground agent loop** (`foreground.py`) — needs the loop shape, but the experiment proves the learning thesis without it. P1.
- **Runtime judge protocol** — control-flow evaluation is real and important, but not prerequisite to proving "does learning improve outcomes?" P1.
- **Real AO artifact completion** — blocked on worker side investigation. Not a controller code problem. P1 (but needs its own investigation).
- **Neatlogs runtime-judge substrate** — research direction, not shipping feature. P2.
- **Hermes-as-sidecar** — already works via `reflection.py`. Dedicated Hermes wiring is polish. P2.
- **Website/core separation** — private repo done. Core removal after 14 Sept per user. Not started.
- **Multi-judge architecture** — aspirational. P2.
- **Agent-native MCP/permission layer** — premature until learning loop is proven. P2.
